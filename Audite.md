# Детальний технічний аудит проєкту Oxide Film

## 1. Архітектурний огляд
Проєкт побудований за принципами **Clean Architecture** з розділенням на Presentation, Domain, Data та Core шари.

### Статистика (приблизна):
*   **Presentation**: ~40% коду (UI логіка, віджети)
*   **Data**: ~40% коду (Провайдери, Парсинг, БД)
*   **Core/Domain**: ~20% коду (Інфраструктура, Моделі)

---

## 2. Детальний аудит по модулях

### 2.1 Mодуль провайдерів контенту (`lib/data/providers`)

Цей модуль є критичним для функціонування додатку, оскільки відповідає за отримання контенту з веб-сайтів.

#### **Загальні проблеми модуля:**
*   🔴 **Single Responsibility Principle Violation**: Класи провайдерів (наприклад, `UaflixProvider`, `EneyidaProvider`) відповідають і за HTTP-запити, і за бізнес-логіку вибору дзеркал, і за парсинг HTML.
*   🔴 **Code Duplication**: Логіка повторних спроб (retry), обробки помилок та форматування URL часто дублюється між провайдерами.
*   ⚠️ **Hardcoded Selectors**: CSS селектори та RegEx вирази "зашиті" прямо в код методів, що ускладнює їх оновлення при зміні верстки сайтів.

#### **Аналіз окремих компонентів:**

*   **`UaflixProvider` (~700 рядків)**
    *   **Проблема**: Методи `_parseDetails` та `_parseSearchResultsStatic` займають левову частку файлу.
    *   **Ризик**: При зміні верстки сайту доведеться редагувати основний клас провайдера, що може зачепити логіку запитів.
    *   **Позитив**: Використання `compute` для винесення парсингу в окремий ізолят.

*   **`EneyidaProvider` (~900 рядків)**
    *   **Проблема**: Складний метод `getStreams` з багатоступінчастою логікою (AJAX -> Iframe -> Script). Це робить метод важким для читання та налагодження.
    *   **Рекомендація**: Розбити стратегії вилучення потоків (Stream Extraction Strategies) на окремі класи (`AjaxStrategy`, `IframeStrategy`).

### 2.2 Модуль UI сторінок (`lib/presentation/pages`)

#### **`HomePage` (`home_page.dart`)**
*   **Аналіз**: Клас `_HomePageState` містить понад 760 рядків коду.
*   **Проблеми**:
    *   **State Management**: Використовується ручне керування станом через `setState` (`_isLoading`, `_error`, `_allItems`). Це призводить до складного коду, який важко тестувати.
    *   **Logic Leakage**: Логіка фільтрації (`_applyFilter`, `_setEquals`) та завантаження даних (`_loadContent`) знаходиться прямо в UI класі.
    *   **Tight Coupling**: Пряма залежність від `GetIt` та сервісів всередині віджета.
*   **Рекомендація**: Використати BLoC (Cubit) для винесення стану (`HomeState`: Loading, Success, Error) та бізнес-логіки.

#### **`PlayerPage` (та інші сторінки перегляду)**
*   **Ризик**: Подібні проблеми з монолітністю, як і в `HomePage`. Ймовірна наявність складної логіки керування відеоплеєром, змішаної з UI версткою.

### 2.3 Модуль сервісів (`lib/data/services`)

#### **`SettingsService`**
*   ✅ **Статус**: Добре спроєктований.
*   **Аналіз**: Чітко розділяє стан (`SettingsState`) та логіку оновлення. Використовує `SettingsDao` для персистентності.
*   **Покращення**: Деякі ключі налаштувань (string literals) варто винести в константи (`SettingsKeys`).

#### **`EpisodeUpdateService`**
*   **Аналіз**: Відповідає за перевірку нових епізодів.
*   **Ризик**: Якщо логіка перевірки стане складною (фонові задачі, сповіщення), цей клас може швидко розростися. Варто розглянути використання `WorkManager` для фонових перевірок.

### 2.4 Модуль віджетів (`lib/presentation/widgets`)

*   **`MediaCard` / `_MediaListTile`**
    *   **Проблема**: Віджети часто визначаються в одному файлі зі сторінкою (як в `home_page.dart`), що робить їх перевикористання неможливим без рефакторингу.
    *   **Рекомендація**: Усі віджети мають бути в окремих файлах.

*   **`FilterSheet`**
    *   **Проблема**: Великий віджет (18 КБ), що містить і UI, і логіку роботи з фільтрами.
    *   **Рекомендація**: Розділити на UI представлення (`FilterView`) та логіку (`FilterController`).

## 4. План рефакторингу (Roadmap)

### Етап 1: Декомпозиція провайдерів (Data Layer)
*   [ ] Створити папку `lib/data/parsers`.
*   [ ] Для кожного провайдера створити окремий парсер (наприклад, `UaflixParser`).
*   [ ] Перенести всю логіку `BeautifulSoup` та RegEx в парсери.
*   [ ] Провайдери мають лише викликати `ApiClient` і передавати HTML в парсер.

### Етап 2: Впровадження BLoC (Presentation Layer)
*   [ ] Почати з `HomePage`. Створити `HomeCubit` та `HomeState`.
*   [ ] Перенести логіку `_loadContent` та фільтрації в Cubit.
*   [ ] `HomePage` має стати `StatelessWidget` або простим `StatefulWidget`, що слухає потік станів.

### Етап 3: Очистка UI коду
*   [ ] Винести всі приватні віджети (наприклад, `_CategoryCard` з `home_page.dart`) в окремі файли в `lib/presentation/widgets/home/`.
*   [ ] Замінити прямі виклики `GetIt` у віджетах на injection через конструктор або `BlocProvider`.

## 6. Глибокий аудит модулів

### 6.1 `EneyidaProvider` (`lib/data/providers/eneyida_provider.dart`)

**Технічні характеристики:**
* **Розмір:** 900 рядків.
* **Відповідальність:** Отримання даних, парсинг HTML, AJAX запити, резолвінг посилань.

#### **Аналіз реалізації:**

1. **Архітектура та SRP:**
   * Клас є класичним прикладом **God Class**. Він поєднує в собі логіку мережевої взаємодії та детальний парсинг DOM-дерева.
   * Використання `ResolvedUrlMixin` для динамічного оновлення домену — це гарне рішення для стабільності.

2. **Логіка парсингу (BeautifulSoup):**
   * **Сильні сторони:** Наявність багатоступеневого пошуку ID (`news_id`, `post_id`, атрибути `article`). Це робить провайдер стійким до дрібних змін у верстці.
   * **Слабкі сторони:** Метод `_parseCardStatic` містить багато RegEx для вилучення року, країни та жанрів. Будь-яка зміна структури картки на сайті призведе до повернення `null` для окремих полів або всього об'єкта.

3. **Вилучення стрімів (getStreams):**
   * Це найскладніша частина модуля. Провайдер використовує 4 послідовні стратегії:
     1. **AJAX Playlist:** Основний метод, що імітує запит плеєра.
     2. **Iframe Parsing:** Пошук вбудованих плеєрів.
     3. **Script Parsing:** Пошук ініціалізації `Playerjs` в коді сторінки.
     4. **Global Parser:** Запуск універсального `PlayerJsParser`.
   * **Проблема:** Така послідовність може бути повільною. Також логіка "лікування" кривих URL (наприклад, подвійні домени `eneyida.tv/eneyida.tv/`) розпорошена по приватних методах.

4. **Продуктивність:**
   * ✅ **compute()**: Всі методи парсингу (`_parseSearchResultsStatic`, `_parseDetailsStatic`, `parseFromHtmlCompute`) викликаються через `compute`, що виключає блокування UI потоку.

5. **Стан і налаштування:**
   * Прапор `_isEnabled` дозволяє динамічно вимикати джерело.
   * Метод `setMirror` дозволяє вручну або автоматично змінювати базовий URL.

#### **Вердикт:**
Модуль функціонально повний та стійкий, але архітектурно перевантажений. Потребує винесення логіки парсингу в `EneyidaHtmlParser` для дотримання принципу розділення відповідальності.

### 6.2 `UaflixProvider` (`lib/data/providers/uaflix_provider.dart`)

**Технічні характеристики:**
* **Розмір:** ~700 рядків.
* **Спеціалізація:** Контент з українським дубляжем (часто Netflix).

#### **Аналіз реалізації:**

1. **Poster Detection (Найкраща практика):**
   * Цей провайдер має найбільш просунуту логіку вилучення обкладинок. Він враховує **lazy-loading** (спочатку перевіряє `data-src`), ігнорує логотипи Netflix та заглушки. Це критично для гарного вигляду UI.

2. **Обробка пошуку:**
   * Реалізовано розділення між форматом карток у пошуку (`a.sres-wrap`) та у каталогах (`div.video-item`). Це свідчить про глибоке розуміння структури сайту.

3. **Iframe & Referer:**
   * ✅ **Правильно**: Провайдер передає заголовок `Referer` при парсингу iframe-ів, що необхідно для обходу захисту деяких плеєрів.

4. **Продуктивність:**
   * ✅ Використовує `compute` для всіх важких операцій.

### 6.3 `UakinoProvider` (`lib/data/providers/uakino_provider.dart`)

**Технічні характеристики:**
* **Розмір:** **1278 рядків** (Критично великий).
* **Складність:** Висока, через агресивне використання AJAX та динамічних плейлистів.

#### **Аналіз реалізації:**

1. **AJAX Пошук та Плейлисти:**
   * Провайдер імітує складні POST-запити до `playlists.php`. Це дозволяє отримувати актуальні посилання, які не доступні при звичайному парсингу HTML.
   * ✅ Використовує `news_id` з різних джерел (input, data-attributes, URL).

2. **Інтелектуальний парсинг епізодів:**
   * Містить детальну логіку (`_parseEpisodeNumber`) з декількома RegEx паттернами для обробки різних форматів написання серій ("Серія", "Епізод", "Ep", "С.").

3. **Корекція якості:**
   * Провайдер має логіку апгрейду якості: якщо URL містить "1080p", а плеєр повернув "unknown", він автоматично виправляє це.

4. **Ризики:**
   * 🔴 **Complexity**: Величезна кількість допоміжних методів (`_cleanPlayerUrl`, `_cleanVoiceoverName`, `_parseQualityFromUrl`) робить файл майже неможливим для підтримки однією людиною.
   * 🔴 **Duplicate Logic**: Багато методів очищення рядків могли б бути винесені в `StringUtils` або базовий клас провайдера.

#### **Вердикт:**
Найпотужніший, але й найбрудніший модуль. Потребує розділення на: `UakinoClient` (API/AJAX), `UakinoParser` (HTML/Regex) та `UakinoStreamResolver`.

### 6.4 `HdrezkaProvider` (`lib/data/providers/hdrezka_provider.dart`)

**Технічні характеристики:**
* **Розмір:** ~1040 рядків.
* **Статус:** ⚠️ Вимкнено (`isEnabled = false`), використовується переважно для метаданих.

#### **Аналіз реалізації:**

1. **Криптографія та декодування:**
   * Провайдер містить унікальну логіку `_decodeStreamUrl` для обходу захисту HDRezka. Він видаляє специфічні "сміттєві рядки" (trash strings, наприклад `//_//JCQhIUAkXiY=`) перед декодуванням Base64.
   * ✅ Наявність `normalizeStreamUrl` для перетворення сегментованих HLS посилань у прямі MP4/M3U8.

2. **Безпека (CSRF):**
   * Це єдиний провайдер, який системно видобуває та передає `csrf-token` у POST-запитах. Це необхідно для роботи з API Rezka.

3. **Багатоступеневий пошук ID:**
   * Використовує 5 різних методів знаходження `dataId` та `translatorId` (Scripts, Init-calls, DOM, URL).

#### **Вердикт:**
Технічно найскладніший провайдер. Потребує регулярного оновлення "сміттєвих рядків". Оскільки він вимкнений, рефакторинг не є пріоритетним, але логіка декодування має бути винесена в окрему утиліту `RezkaDecoder`.

### 6.1 `EneyidaProvider` (`lib/data/providers/eneyida_provider.dart`)

**Технічні характеристики:**
* **Розмір:** 900 рядків.
* **Відповідальність:** Отримання даних, парсинг HTML, AJAX запити, резолвінг посилань.

#### **Аналіз реалізації:**

1. **Архітектура та SRP:**
   * Клас є класичним прикладом **God Class**. Він поєднує в собі логіку мережевої взаємодії та детальний парсинг DOM-дерева.
   * Використання `ResolvedUrlMixin` для динамічного оновлення домену — це гарне рішення для стабільності.

2. **Логіка парсингу (BeautifulSoup):**
   * **Сильні сторони:** Наявність багатоступеневого пошуку ID (`news_id`, `post_id`, атрибути `article`). Це робить провайдер стійким до дрібних змін у верстці.
   * **Слабкі сторони:** Метод `_parseCardStatic` містить багато RegEx для вилучення року, країни та жанрів. Будь-яка зміна структури картки на сайті призведе до повернення `null` для окремих полів або всього об'єкта.

3. **Вилучення стрімів (getStreams):**
   * Це найскладніша частина модуля. Провайдер використовує 4 послідовні стратегії:
     1. **AJAX Playlist:** Основний метод, що імітує запит плеєра.
     2. **Iframe Parsing:** Пошук вбудованих плеєрів.
     3. **Script Parsing:** Пошук ініціалізації `Playerjs` в коді сторінки.
     4. **Global Parser:** Запуск універсального `PlayerJsParser`.
   * **Проблема:** Така послідовність може бути повільною. Також логіка "лікування" кривих URL (наприклад, подвійні домени `eneyida.tv/eneyida.tv/`) розпорошена по приватних методах.

4. **Продуктивність:**
   * ✅ **compute()**: Всі методи парсингу (`_parseSearchResultsStatic`, `_parseDetailsStatic`, `parseFromHtmlCompute`) викликаються через `compute`, що виключає блокування UI потоку.

5. **Стан і налаштування:**
   * Прапор `_isEnabled` дозволяє динамічно вимикати джерело.
   * Метод `setMirror` дозволяє вручну або автоматично змінювати базовий URL.

#### **Вердикт:**
Модуль функціонально повний та стійкий, але архітектурно перевантажений. Потребує винесення логіки парсингу в `EneyidaHtmlParser` для дотримання принципу розділення відповідальності.

*   **Сильні сторони**: Використання Drift (SQL) забезпечує надійність збереження даних. Реалізовано реактивність через `watchAllSettings()`, що дозволяє інтерфейсу миттєво оновлюватися при зміні будь-якого параметра. Підтримує складні вкладені структури, такі як `UISettings`.
*   **Слабкі сторони (Технічний борг)**:
    *   **Монолітний стан**: `SettingsState` містить понад 20 полів. Будь-яка зміна (наприклад, перемикання одного чекбокса) призводить до перерахунку всього об'єкта стану та сповіщення всіх слухачів (`notifyListeners`), що може бути неефективним.
    *   **Перевантаження `providerStates`**: Мапа `providerStates` використовується для збереження двох різних типів даних: прапорця увімкнення провайдера та прапорця "пошук дозволено" (з префіксом `search_enabled_`). Це створює плутанину в логіці та ускладнює типізацію.
    *   **Відсутність Type Safety в БД**: Більшість налаштувань зберігаються як String у таблиці `AppSettings`. Хоча в Dart вони представлені перерахуваннями (enums), на рівні бази даних немає жодних обмежень, що може призвести до помилок парсингу при некоректних даних.
    *   **Ручне парсування**: Метод `_updateStateFromSettings` містить величезну кількість `double.tryParse`, `int.tryParse` та тернарних операторів для встановлення дефолтних значень. Це важко підтримувати та легко зламати при додаванні нових параметрів.
    *   **Надмірний бойлерплейт**: Додавання одного нового налаштування вимагає змін у 5-6 місцях: `SettingsState`, конструктор, `copyWith`, `_updateStateFromSettings`, метод-сеттер та DAO.
    *   **Тестування**: Через пряму залежність від `SettingsDao` та `AppDatabase` у конструкторі, сервіс важко тестувати в ізоляції без мокування всієї бази даних.
*   **Пропозиції щодо покращення**: Розділити `SettingsState` на менші логічні частини (ThemeState, PlayerState тощо). Перейти до використання структурованих JSON-об'єктів для складних налаштувань замість плоскої таблиці ключ-значення.

### 2.10 WatchPartyService (`watch_party_service.dart`)
*   **Призначення**: Забезпечує функціонал "Watch Party" (спільний перегляд) з синхронізацією відтворення.
*   **Сильні сторони**: Реалізовано надзвичайно складний та надійний протокол синхронізації з багаторівневою корекцією дрифту (None, Smooth, Fast, Hard Seek). Наявність гібридної системи бекендів (Supabase Cloud + PeerDart P2P як фолбек) робить сервіс стійким до проблем із сервером.
*   **Слабкі сторони (Технічний борг)**:
    *   **God Class**: Клас налічує близько 1200 рядків коду, поєднуючи в собі логіку мережевої взаємодії, керування станом кімнати, синхронізацію відео та чат.
    *   **Брихкий парсинг повідомлень**: Обробка вхідних повідомлень у `_onMessageReceived` базується на великому `switch-case` та ручному приведенні типів `payload as Map<String, dynamic>`. Це робить систему вразливою до помилок при зміні протоколу.
    *   **Presence Complexity**: Робота з `Supabase Presence` містить багато низькорівневої ітерації по "raw state entries", що, згідно з коментарями, було складно налагодити (migration issues).
    *   **Відсутність персистентності стану**: Стан кімнати, учасники та чат зберігаються лише в пам'яті (`RAM`). При перезавантаженні додатка користувач втрачає всю історію переписки та список учасників, навіть якщо з'єднання відновлюється.
    *   **Dependency Injection**: Сервіс використовує `GetIt.I<SettingsService>()` безпосередньо всередині методів, що створює приховане зачеплення (tight coupling) та ускладнює написання юніт-тестів.
    *   **Продуктивність**: Виклик `notifyListeners()` при отриманні кожного повідомлення про синхронізацію (кожні 2 секунди) може негативно впливати на продуктивність UI, якщо в кімнаті багато учасників.
    *   **Компенсація затримки**: Хоча враховується `networkDelay`, метод оцінки базується на локальному системному часі пристроїв, який може не збігатися, що додає похибку в синхронізацію.
*   **Пропозиції щодо покращення**: Винести бекенди в окремі класи-стратегії (що вже частково зроблено, але потребує глибшої декомпозиції). Впровадити формальну схему повідомлень (наприклад, через `sealed classes` у Dart 3).

### 2.11 Database Layer (AppDatabase & DAOs)
*   **Призначення**: Забезпечує локальне збереження всіх даних програми (історія, обране, завантаження).
*   **Сильні сторони**: Використання бібліотеки Drift забезпечує повну типізацію SQL-запитів. Чітка структура таблиць з унікальними ключами (наприклад, для `WatchHistory` враховується сезон та епізод).
*   **Слабкі сторони (Технічний борг)**:
    *   **Складність міграцій**: Вже на 5-й версії схеми логіка `onUpgrade` містить складні SQL-скрипти з тимчасовими таблицями (`downloads_new`). Це свідчить про те, що первісна структура була недостатньо гнучкою.
    *   **Бойлерплейт DAOs**: Кожен DAO (History, Favorites, Downloads) має дубльовану логіку мапінгу об'єктів бази даних у доменні сутності.
    *   **Cleanup Logic**: Логіка очищення даних (наприклад, видалення провайдера Filmix у міграції v5) зашита безпосередньо в код бази даних, що робить міграцію "важкою" при великих обсягах даних.
    *   **Search History**: Таблиця `SearchHistoryTable` зберігає лише успішні запити. Відсутність збереження невдалих запитів обмежує можливості аналітики для покращення парсерів.
    *   **Unique Keys**: Використання `mediaId + providerId` як унікального ключа є правильним, але в деяких таблицях це не поширюється на `season/episode`, що може призвести до перезапису прогресу різних серій одного серіалу.
    *   **Відсутність індексів**: Хоча є `uniqueKeys`, бракує явних індексів для полів, за якими часто йде фільтрація (наприклад, `mediaType` або `watchedAt`), що може сповільнити роботу при тисячах записів в історії.
*   **Пропозиції щодо покращення**: Впровадити автоматизоване тестування міграцій. Винести SQL-скрипти міграцій в окремі ресурси. Додати індекси для частих запитів.
* **Технології:** Supabase Realtime, PeerDart (P2P).

#### **Аналіз реалізації:**

1. **Алгоритм синхронізації:**
   * ✅ **Поетапне виправлення (Drift Recovery)**: Сервіс не просто перестрибує на потрібний час, а використовує зміну швидкості відтворення (1.1x / 1.2x), що робить процес синхронізації непомітним для користувача.
   * ✅ **Гард-сік (Hard Seek)**: Використовується лише при великому розриві (>10с).

2. **Відмовостійкість:**
   * ✅ Реалізовано прозорий фолбек: якщо Supabase недоступний, додаток автоматично перемикається на Peer-to-Peer з'єднання через PeerDart.

3. **Ризики:**
   * 🔴 **Complexity**: Клас перевантажений логікою протоколів, управлінням кімнатами та обробкою чату. Потребує розділення на `WatchPartyCore` та `SyncEngine`.

## 8. Гіпер-глибокий аудит: Логічні вразливості та мікро-оптимізації

Цей розділ фокусується на конкретних рядках коду, де логіка може бути покращена для більшої стабільності.

### 8.1 Data Providers: Вразливості парсингу

*   **`EneyidaProvider` & `UaflixProvider` (Year extraction):**
    *   **Проблема:** Використання широких регулярних виразів типу `RegExp(r'(\d{4})')` на всьому тексті картки. Це може призвести до хибного вибору року, якщо в описі є інші числа (наприклад, "Роздільна здатність 1080p").
    *   **Покращення:** Обмежити пошук лише певними HTML-елементами (наприклад, тільки тими, що мають клас `year` або `short-info`).

*   **`UakinoProvider` (Unicode Decoding):**
    *   **Проблема:** Ручна реалізація декодування Unicode `\uXXXX` у методі `_cleanVoiceoverName`.
    *   **Покращення:** Використовувати бібліотеку `html_unescape` або стандартний `jsonDecode` для надійної обробки всіх спецсимволів.

*   **`HdrezkaProvider` (Decryption Brittleness):**
    *   **Проблема:** Логіка видалення "сміттєвих рядків" (`knownTrash`) базується на статичному списку. Якщо HDRezka змінить алгоритм обфускації, цей провайдер миттєво зламається.
    *   **Покращення:** Створити механізм динамічного оновлення паттернів обфускації через зовнішній конфіг.

### 8.3 Services: Архітектурні мікро-ризики

*   **`WatchPartyService` (Clock Drift):**
    *   **Проблема:** Розрахунок затримки мережі базується на `DateTime.now().difference(hostTimestamp)`. Це припускає, що годинники на пристрої Хоста та Гістя ідеально синхронізовані, що майже ніколи не буває правдою.
    *   **Покращення:** Впровадити NTP-синхронізацію або розраховувати затримку через Round-Trip Time (RTT) за протоколом "ping-pong".

*   **`SettingsService` (Mapping Overhead):**
    *   **Проблема:** Кожен параметр налаштувань вручну мапиться з рядка в об'єкт у `_updateStateFromSettings`. Це створює "Boilerplate Hell" при додаванні нових налаштувань.
    *   **Покращення:** Використовувати `json_serializable` для мапінгу всього стану налаштувань одним викликом.

### 8.4 UI Layer: Продуктивність та Адаптивність

*   **`HomePage` (Sequential Loading):**
    *   **Проблема:** Провайдери опитуються послідовно в циклі `for (final provider in providers)`. Загальний час завантаження дорівнює сумі часів відповіді всіх сайтів.
    *   **Покращення:** Використовувати `Future.wait()`, щоб запити до всіх провайдерів йшли паралельно. Це скоротить час завантаження головної сторінки в 3-4 рази.

*   **`Player UI` (Responsive Brittleness):**
    *   **Проблема:** Хардкодні обчислення `fontSize` та `padding` у `_buildTopBar` на основі `MediaQuery`.
    *   **Покращення:** Використовувати `ScreenUtil` або винести ці константи в систему `ResponsiveUtils`, щоб уникнути спагетті-коду в методі `build`.

*   **`Player UI` (Global State Rebuilds):**
    *   **Проблема:** Зміна синхронізації у `WatchParty` викликає повний `setState` всього плеєра через лісенери.
    *   **Покращення:** Використовувати `RepaintBoundary` (вже частково є) та `ValueNotifier` для оверлеїв, щоб не перемальовувати важкий віджет відео при зміні тексту в чаті або статусів синхронізації.

### 8.5 Shared Utilities: Надійність PlayerJS

*   **`PlayerJsParser` (Brute-force Decoding):**
    *   **Покращення:** Метод `_decodePlayerJsString` використовує перебір (Base64, Caesar Shift, Hex). Це дуже надійний підхід для існуючих сайтів.
    *   **Ризик:** Відсутність кешування результатів декодування. Якщо на сторінці багато закодованих посилань, `compute` (Isolate) створюється на кожен виклик, що може бути накладним.
    *   **Покращення:** Впровадити `LRUCache` для результатів декодування.

### 8.6 Core Logic: Incomplete Sync Module

*   **`lib/core/sync/sync.dart` (Placeholder state):**
    *   **Проблема:** Модуль містить лише експорти та великі `TODO` щодо WebRTC та Signaling. Поточна реалізація `WatchPartyService` знаходиться в `data/services` і використовує сторонні рішення (Supabase/PeerDart), тоді як ядро синхронізації (`core/sync`) пустує.
    *   **Рекомендація:** Об'єднати ці зусилля. Поточна робоча реалізація має стати частиною `core/sync` після рефакторингу.

    *   **Проблема:** Кожен параметр налаштувань вручну мапиться з рядка в об'єкт у `_updateStateFromSettings`. Це створює "Boilerplate Hell" при додаванні нових налаштувань.
    *   **Покращення:** Використовувати `json_serializable` для мапінгу всього стану налаштувань одним викликом.

### 8.4 UI Layer: Продуктивність та Адаптивність

*   **`HomePage` (Sequential Loading):**
    *   **Проблема:** Провайдери опитуються послідовно в циклі `for (final provider in providers)`. Загальний час завантаження дорівнює сумі часів відповіді всіх сайтів.
    *   **Покращення:** Використовувати `Future.wait()`, щоб запити до всіх провайдерів йшли паралельно. Це скоротить час завантаження головної сторінки в 3-4 рази.

*   **`Player UI` (Responsive Brittleness):**
    *   **Проблема:** Хардкодні обчислення `fontSize` та `padding` у `_buildTopBar` на основі `MediaQuery`.
    *   **Покращення:** Використовувати `ScreenUtil` або винести ці константи в систему `ResponsiveUtils`, щоб уникнути спагетті-коду в методі `build`.

*   **`Player UI` (Global State Rebuilds):**
    *   **Проблема:** Зміна синхронізації у `WatchParty` викликає повний `setState` всього плеєра через лісенери.
    *   **Покращення:** Використовувати `RepaintBoundary` (вже частково є) та `ValueNotifier` для оверлеїв, щоб не перемальовувати важкий віджет відео при зміні тексту в чаті або статусів синхронізації.
