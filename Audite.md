# Звіт аудиту проєкту Oxide Film

## 1. Аналіз структури та залежностей

### Загальна інформація
- **Назва**: oxide_film
- **Версія**: 1.0.20260201+20260201
- **Технологічний стек**: Flutter (SDK ^3.10.7)

### Основні бібліотеки
- **State Management**: flutter_bloc, equatable - стандартний вибір, надійно.
- **Routing**: go_router - рекомендовано Flutter командою.
- **Networking**: dio, dio_smart_retry, connectivity_plus - хороший набір.
- **Parsing**: html, beautiful_soup_dart, universal_html - достатньо для скрапінгу.
- **Player**: media_kit - потужний крос-платформний плеєр.
- **Database**: drift - потужна ORM для SQLite.
- **DI**: get_it, injectable - стандарт де-факто.

### Зауваження до налаштувань
- **analysis_options.yaml**: Використовується базовий набір `flutter_lints`. Рекомендується розширити правила лінтера для забезпечення кращої якості коду та уніфікації стилю (наприклад, додати `prefer_const_constructors`, `always_declare_return_types`, тощо).
- **Hard-coded version**: Версія прописана в pubspec.yaml. Для CI/CD краще використовувати аргументи збірки.
- **Dependency Versions**: Версії залежностей зафіксовані доволі жорстко (caret syntax). В цілому ок, але варто слідкувати за major updates.

## 2. Аудит модулів

### Core (`lib/core`)

- **DI (`di/injection.dart`)**: Використовується `get_it` та `injectable`. Код чистий, реєстрація залежностей прозора.
- **Network (`network/api_client.dart`)**:
    - Обгортка над `Dio` з використанням singleton.
    - Реалізована логіка повторних запитів (`RetryInterceptor`), що критично для нестабільних джерел.
    - **Покращення**: `User-Agent` жорстко заданий в коді. Рекомендується винести в конфігурацію (наприклад, Remote Config) для можливості динамічного оновлення без перезбірки додатку, оскільки парсери часто блокуються по UA.
- **Config (`config/app_config.dart`)**: Константи винесені. API ключ TMDB не заданий за замовчуванням (що правильно з точки зору безпеки git).
- **Загальне**: Clean Architecture дотримується. Модуль містить лише інфраструктурні компоненти.

### Data (`lib/data`)

- **Providers (`providers/*`)**:
    - Реалізовано низку провайдерів (UAKino та ін.).
    - Парсинг (на прикладі `UakinoProvider`) виконаний детально, з обробкою AJAX та різних типів контенту.
    - **Проблема**: Використання `print` замість `Logger` у багатьох місцях. Це засмічує консоль і ускладнює відладку в релізній версії.
    - **Ризик**: Логіка парсингу прив'язана до DOM-структури сайтів. Це крихке місце, яке потребує регулярної підтримки. Варто розглянути можливість винесення CSS-селекторів у конфіг або серверний компонент.
- **Database (`database/app_database.dart`)**:
    - Використовується `drift`. Схема бази даних чітка (`Favorites`, `WatchHistory`, `Downloads`, `Settings`).
    - Реалізована міграція (версія 2).
    - DAO винесені окремо, що добре для структури.

### Domain (`lib/domain`)

- **Entities**:
    - Моделі (`MediaItem`, `StreamSource`) реалізовані з використанням `Equatable`, що правильно для порівняння об'єктів.
    - В Enum-класи винесена локалізація (`displayName`), що спрощує використання в UI.
- **Repository Interfaces**: (Перевірено в коді провайдерів) Визначені чітки контракти для отримання даних.

### Services (`lib/data/services`)

- **DownloadService**:
    - Забезпечує офлайн-перегляд. Має власний менеджер завдань.
    - **Зауваження**: Використовує пакет `http` для завантаження файлів, тоді як решта додатку працює через `Dio` (`ApiClient`). Це створює неузгодженість. `Dio` краще підходить для завантажень (вбудований cancel token, progress stream, interceptors).
- **SyncService**:
    - Реалізує backup/restore функціонал через JSON. Простий і ефективний підхід для локальної бази.

### Presentation (`lib/presentation`)

- **Pages (`DetailsPage`, `PlayerPage`)**:
    - **Архітектурна проблема**: Використання `GetIt` безпосередньо у віджетах (`_DetailsPageState`). Це порушує принцип розділення відповідальності та ускладнює тестування. Рекомендується використовувати `BlocProvider` та впроваджувати залежності через конструктори Bloc-ів.
    - **UI Logic**: Бізнес-логіка (завантаження деталей, збереження прогресу) знаходиться всередині `StatefulWidget`. Варто винести це в Cubit/Bloc.
    - **Player**: Використання `media_kit` реалізовано коректно. Таймери для збереження прогресу очищуються в `dispose`, що запобігає витоку пам'яті.
    - **Адаптивність**: Є базова підтримка десктопу/мобайлу (`_isDesktop`), але краще використовувати `LayoutBuilder` або спеціалізовані пакети для адаптивності.

### Utils & Config

- **Logger**: Є клас `Logger`, але він мало використовується. Багато `print` та `debugPrint`.

## 3. Висновки та Рекомендації

Проєкт має міцний фундамент та використовує сучасний стек технологій. Основні архітектурні рішення (Clean Architecture, Drift, MediaKit) є правильними. Однак є певні відхилення в реалізації UI шару та чистоті коду.

### Пріоритетні завдання:
1.  **Refactoring UI Logic**: Винести логіку з `StatefulWidget` (особливо в `DetailsPage` та `PlayerPage`) у BLoC/Cubit.
2.  **Logging**: Замінити всі `print` на `Logger`.
3.  **Network Client**: Уніфікувати роботу з мережею (перевести `DownloadService` на `Dio`).
4.  **Error Handling**: Покращити відображення помилок користувачеві (зараз часто просто логується в консоль).
5.  **User-Agent**: Винести UA в конфіг, що оновлюється віддалено.

## 4. Глибокий аудит (Deep Dive Audit)

### 4.1. Парсинг та Провайдери (`lib/data/providers`, `lib/data/parsers`)

*   **PlayerJsParser**:
    *   **Реалізація**: Використовує Regex (`filepattern`, `encodedPattern`) для витягування потоків.
    *   **Ризик**: Regex парсинг HTML/JS коду є крихким. Якщо сайт трохи змінить формат (наприклад додасть пробіл або змінить лапки), парсер зламається.
    *   **Декодування**: Методи декодування (`_decodePlayerJsString`) реалізовані евристично (Base64, Caesar Shift). Це "чорна скринька", яка може застаріти будь-якої миті.
*   **HdrezkaProvider**:
    *   **Дзеркало**: URL `https://hdrezka.ag` жорстко зашитий в коді. Це гарантує, що додаток перестане працювати при блокуванні цього дзеркала.
    *   **Дані**: Списки жанрів та країн захардкоджені в провайдері. Це дублюється в `ContentFilter`, що веде до розсинхронізації.
    *   **Структура сайту**: Сильна залежність від CSS класів (`b-content__inline_item`, `b-post__title`). Будь-яка зміна верстки зламає додаток.
*   **FilmixProvider**:
    *   **API**: Використовує API ендпоінт (`api/v2/post`) для отримання посилань, що набагато надійніше за скрапінг.
    *   **Дублювання**: Логіка `_parseSearchResults` майже ідентична до `HdrezkaProvider`. Варто винести загальні методи парсингу (наприклад, `MediaCardParser`) в базовий клас або утиліту.

### 4.2. Налаштування та Persistence

*   **SettingsService & DAO**: Реалізація чиста і правильна. Використання `Drift` для збереження налаштувань - good practice.
*   **ContentFilter**:
    *   **Фільтрація**: Логіка `apply` виконується на клієнті. Для великих списків це може бути повільно, але для поточної пагінації (сторінками) це прийнятно.
    *   **Дублювання даних**: Списки `Genres.slugs` та `Countries.all` продубльовані тут і в окремих провайдерах. Це **High Maintainability Risk**. Треба створити єдине джерело істини (наприклад, конфігураційний файл або глобальні константи в `Core`).

### 4.3. Відеоплеєр (`PlayPage`)

*   **MediaKit**: Використовується ефективно.
*   **Проблеми (Critical/Major)**:
    *   **Відсутній Wakelock**: Екран пристрою може вимкнутись під час перегляду фільму, оскільки немає виклику `WakelockPlus.enable()`. Це критична проблема UX.
    *   **Фонові процеси**: Немає інтеграції з `audio_service`. Якщо згорнути додаток, звук, ймовірно, продовжить грати або зупиниться некоректно (залежить від OS), але контролю в шторці повідомлень не буде.
    *   **Субтитри**: Реалізована лише зміна "Озвучки" (яка по суті є перемиканням потоків). Якщо потік містить вбудовані субтитри (embedded srt/vtt), користувач не може їх увімкнути/вимкнути.
    *   **Помилки**: Немає обробки помилок при `_player.open()`. Якщо потік недоступний (404/Geoblock), користувач побачить нескінченний спінер.

### 4.4. Завантаження (`DownloadService`)

*   **Networking**: Використовується `http` клієнт, тоді як весь інший додаток на `Dio`. Це inconsistency. `Dio` дозволяє легше керувати прогресом і скасуванням.
*   **Файлова система**:
    *   Файли зберігаються в `getApplicationDocumentsDirectory`. Це безпечно, але користувач не має прямого доступу до файлів (щоб відкрити в VLC, наприклад).
    *   Немає перевірки вільного місця на диску перед початком завантаження.
    *   Немає обробки ситуації зміни мережі (Wi-Fi -> Mobile Data) під час завантаження.

### 4.5. UI/UX та Навігація

*   **GoRouter**: Конфігурація чиста, підтримує deep linking (`/details/:id`) та extra objects. Все зроблено правильно.
*   **Theme**: Гарна реалізація теми через статичні методи. Підтримка AMOLED режиму - великий плюс для media-додатку.
*   **Watch Party**:
    *   Цікава фіча. Використовує сокети? (потрібен детальніший погляд на сервіс). UI виглядає функціональним, але UX підключення через IP:Port (`192.168.x.x`) занадто складний для пересічного користувача. Варто розглянути використання QR-кодів або mDNS/Bonjour для автопошуку в локальній мережі.

## 5. Фінальні Рекомендації (Action Plan)

### High Priority (Критичні з покращення UX/Stability)
1.  **Wakelock**: Додати `wakelock_plus` в `PlayerPage` (`enable` в `initState`, `disable` в `dispose`).
2.  **Обробка помилок плеєра**: Додати слухач `_player.stream.error` і показувати діалог/snackbar, якщо відео не вантажиться.
3.  **Дублювання списків**: Винести списки жанрів та країн в `lib/core/constants/content_constants.dart` і використовувати їх всюди (Filter, Providers).
4.  **Logging**: Повсюдна заміна `print()`, особливо в циклах парсингу, на `Logger` з продуманими рівнями логування (Warning при фейлі парсингу одного елементу, Error при падінні всієї сторінки).

### Medium Priority (Покращення архітектури)
1.  **Network Unification**: Переписати `DownloadService` на `Dio`.
2.  **Remote Config for Parsers**: Винести CSS селектори та regex-паттерни в JSON конфіг, який можна завантажувати з Firebase/GitHub Gist при старті. Це дозволить лагодити парсери без випуску оновлення в стор.
3.  **Watch Party UX**: Додати QR-код генератор/сканер для швидкого підключення.
4.  **UI Refactoring**: Почати міграцію `DetailsPage` на `Cubit`.

### Low Priority (Полірування)
1.  **Linter Rules**: Зробити лінтер суворішим.
2.  **Unit/Widget Tests**: Почати покривати тестами парсери (завантажити зразки HTML сторінок і написати тести на парсинг).
